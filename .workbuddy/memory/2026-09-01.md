## ⚠️ wxss 编译报错修锅（用户报截图："编译 .wxss 文件错误"）

### 现象
用户开微信开发者工具时弹"编译 .wxss 文件错误，请到开发者工具控制台查看更详细信息"——上一轮校验脚本（基于 vm 沙箱、不真编译 wxss）**没有抓到这个错误**。

### 根因（asklake.wxss 第 86–87 行）
```
.lk-cx-g .al-eico { width:36rpx; height:36rpx; }
  margin-bottom:26rpx; }       ← 没有选择器的孤立属性 + 孤立闭花括号
```
之前我用 Edit 工具替换「结局图标」CSS 块时，把原本一条完整的 `.lk-cx-g .al-eico { width:36rpx; height:36rpx; margin-bottom:26rpx; }` 错拆成两段，**第二段漏了选择器开头、只剩 `margin-bottom:26rpx; }`**——整个 wxss 解析失败。

### 修复
删掉孤立行 → `.lk-cx-g .al-eico { width:36rpx; height:36rpx; }` 紧接下一条规则 `.lk-ebody { ... }`。`_sc_wxchk.cjs` 19/19 仍通过。

### 教训（沉淀）
1. **vm 校验脚本抓不到 wxss 编译错误**——只能覆盖 js 逻辑层；wxss/wxml 真编译必须靠微信开发者工具。**校验脚本 PASS ≠ 真机能 PASS**，交付给用户前最好让 IDE/CLI 真扫一遍（或者写个最小的 wxss 语法检查器：花括号配对 + 每条规则必须有 selector）。
2. **Edit 工具替换 CSS 块时务必整段替换**：不要把一条规则的属性跨多条替换、不要在替换边界丢字符；新字符串与旧字符串 `{}`/`;` 数量应对得上。
3. 之前还有一条同源教训："插入多行内联 SVG/HTML 字符串后必跑 `node --check game.js`"——CSS 没 `node --check`，要靠眼睛 + IDE 自动编译来兜底。

## 站位「4号位重复」根因 + 永久座位号 seatNo

### 用户反馈
- 截图实测：「巨寇·董三更 四号位」与「我方行棋中·董三更 四号位」**同时出现**两遍"四号位"。
- 之前虽有位置号，但 boss push / siege 多波 born 之后，玩家座位号被 state.players.indexOf 算出重复。

### 根因（双层）
1. **`state.players.findIndex(x=>x.id===pl.id)+1` 会飘移**：boss 模式把 boss push 到 players 末尾 → 老玩家 index 整体后移；siege 每波加 2 个 born 同样推 index。**入场序号 ≠ 永久座位号**。
2. **`startGame` 顺序错位**：`const players = keys.map(makePlayer)` 在 `state = {...}` **之前** 调用，导致首次 makePlayer 时 `if(state)` 失败，所有玩家分到 seatNo=0。仅第 4 次（boss push）时 state 已存在，才偶然成功分到 1。→ 这就是"巨寇四号位"的真实来源。

### 修复
- **state.seatCounter 全局递增**，每 `makePlayer` 自增一次，**永久 seatNo** 写入 player 对象。
- **startGame 顺序调整**：`state = {...seatCounter:0}` 必须在 `players = keys.map(makePlayer)` 之前。
- **enemyCard / heroBody** 改用 `pl.seatNo` 直接渲染位置号（不再依赖 indexOf）。
- **小程序 engine.js 同步**：`seatLabelOf(pl)` 改读 `pl.seatNo`。

### 强化视觉（按参考图）
- 位置号：金底深字（gradient #f4d994→#c9a24b），加粗，字号 13px（PC）/ 22rpx（小程序），不再"小字黑底"。
- 阵亡大字：42px（PC）/ 62rpx（小程序），白字压立绘中央 + 强文字阴影 + 半透黑底衬。
- hero 中央卡的位置号放右上角（不和 hero-badge 冲突），样式更显眼。

### 验证（针对性 + 全量）
- **针对性 vm 测试**：boss 4 人 seatNo 1~4 唯一 ✓；siege 1/2/3 波 4/6/8 人单调递增且唯一 ✓。
- **renderGame 验证**：4 个 seat-num 标签齐全（一号位 hero + 二三四号位 对位/队友），ph-dead 开局 0 个。
- **两端 smoke 不回归**：PC 12/12 ✓ · 小程序 19/19 ✓。
- 缓存 bump `game.js?v=20260901g → h → i`（连续 bump 防浏览器缓存）。

### 教训沉淀（MEMORY 第二/七节）
- **「座位号」= 永久入场序号字段，不= state.players 数组 index**。所有"按位置排"的视觉（位置号、加入顺序徽章、座位指示）必须用持久字段，不能依赖数组下标。
- **startGame 的"先建 state 再建 player"是铁序**：任何新建对象 hook 都要保证它在 state 已初始化之后才能生效，否则会沉默地 fallback 到 undefined 路径。

## 双模块「本旬结算中转页」落地（B 方案：山水祠 + 落魄山都加）

## 「过此旬」冗余点击 → 本旬已尽自动进中转页

### 用户质疑（原话）
"我选完最后一个问题不就自动进入中转页了吗？为什么你的逻辑这么奇怪，能不能梳理下交互"

### 认错：此前论证有漏
- 我先前以"一旬多桩、选一项只是解此桩"论证「过此旬」按钮必要 —— 结论没错，但**漏了终态**。
- 真实数据：`apMax=3`；开局 `scStart` 只抽 **2 桩**（`scDealWishes(s,2)`），后续旬抽 3~4 桩。
- **行动力是所有主动行为的唯一门票**：`ap<=0` 时 解祈愿 / 巡山 / 养气 / 请天劫 **全部失效**（解祈愿 `ok: rq.ok && !apOut`；巡山养气 `canXxx: s.ap>0 && ...`；请劫 `s.ap<=0 return`）。
- 于是"解完最后一桩 → ap 归零 → 全屏只剩「过此旬」能点 → 还要手动点一次才结算" = **纯冗余点击**。必然发生的事不该要玩家确认。

### 真实一旬循环（梳理后）
```
入旬：xun++ / ap=3 / 抽 3~4 桩（开局 2 桩）
  ├─ 主舞台一次只呈一桩（events[0]），显示"第1桩/共N桩"
  ├─ 应（resolve）  → ap--、事件出队
  ├─ 不应（skip）   → backlog++、信心-4（不耗 ap）
  └─ 祠务抽屉：巡山(-8香火)、养气(-20香火)、请天劫 —— 均 ap--
本旬已尽（无事可做）→ 自动 scSettle() → 中转页（账本）
  └─ 点「入下一旬」→ scEnterNext() → 下一旬
```

### 实现（双端同构）
- 新增 `scCanTianjie(s)` / `scXunExhausted(s)` / `scMaybeAutoSettle(s)`。
  - 判定：`ap<=0` 即已尽；否则须 `events 空 && !canPatrol && !canNourish && !canTianjie`。
  - **天劫例外**：`ap<=0` 但队列压着 `tianjie` → 不自动结算（天劫是大事，不能被账本跳过）。
  - `scMaybeAutoSettle` 延迟 **900ms** 再 `scSettle()` —— 留一拍让飘字/叙事先落地，免得刚做完的结果被吞。
- 挂载到 5 个出口：`scAfterEvent`（resolve 统一出口）/ `scSkipEvent` / `scPatrol` / `scNourish` / `scRequestTianjie`。
- **护栏**：这 5 个函数首行统一加 `if(s.over || s.settling) return;`（此前只查 `over`，中转页状态下理论上仍可被调用）。
- **顺带修隐患**：请天劫原为 `ap>0` 即可，但请劫(1点)+应劫(1点)共需 2 点 → 只剩 1 点时会"请了天劫却无力应劫"，天劫卡死在队列。现 `scCanTianjie` 要求 `ap>=2`，UI 侧同步：小程序 `canAsk: s.ap>=2` + 文案"行动力不足 · 请天劫与应天劫各需一点"；PC 端按钮 `scCanTianjie(s)` 判定 + 同款提示。
- 缓存：`index.html` `shenci.js?v=20260901g→h`。

### 校验
- 专项 `_sc_auto_settle_test.cjs`（**真实 setTimeout**，14 项）连跑 3 次稳定全绿，验证：香火充足仍有养护可做→不结算 / 解完最后一桩无力再养护→结算 / 典型旬 3桩vs3ap→解完即结算 / 天劫不被跳过 / 请劫门槛 2 点 / settling 状态下巡山·养气·不应均被拦下。**跑完即删**。
- `node --check` 双端 OK；`_sc_smoke.cjs` **12/12**；`_sc_wxchk.cjs` **19/19**；`_sc_sim.cjs` 平衡采样各策略结局分布正常。

### 教训（写入 MEMORY）
1. **必然发生的操作不要做成按钮**。判断标准：`ap<=0` 后所有分支都汇向同一结果 → 该结果是"必然"，不该要确认；真正的按钮只留给"是放弃剩余行动力提前收工"这类真实选择。
2. **`_sc_wxchk.cjs` 里 `setTimeout` 被打桩成 `()=>0`** → 任何依赖定时器的新逻辑在该套件里都是**假绿灯**。改定时器相关行为必须另写真实定时器的专项脚本，并连跑多次查抖动。
3. 自动化测试的断言不要写死中间假设（我曾断言"ap 有剩就绝不结算"，实际"香火不足以养护"时也算无事可做）——先跑一次看真实行为再定断言。

## 中转页入场动效（用户："中转页是不是做点动效"）

### 动效设计：卷轴铺开 · 逐行落账（四端同步：山水祠/落魄山 × PC/小程序）
时间轴（总时长约 1.3s，按钮 .88s 起浮现，位置从一开始就占好、不会布局跳动）：
| 时序 | 元素 | 动效 |
|---|---|---|
| 0s / .56s | `.st-head`「本 旬 已 了」 | `stSeal`：scale 1.14→1 + letter-spacing 26→10 + blur 6→0（墨迹落定，非光晕） |
| .22s / .46s | `.st-sub` 旬序季 | `stFadeUp`：下移 14→0 + 淡入 |
| .30s / .42s | `.st-ledger` 账本框 | `stUnroll`：scaleY .62→1，`transform-origin:top center`（自上铺开） |
| .42~.82s / .34s | `.st-row` 逐行 | `stRowIn`：左移 -14→0 + blur 3→0，nth-child(1..5) 每行 +.08s 错峰，`n+6` 兜底 |
| 行 +.08s / .28s | `.st-v` 数值 | `stNumIn`：scale 1.16→1 定格 |
| .80 / .84 / .88s | notes / backlog / 按钮 | `stFadeUp` 收尾 |

- 小程序用 rpx（translateY 16rpx、blur 6rpx…），PC 用 px（14px、6px…），keyframes 名统一为 `stSeal/stFadeUp/stUnroll/stRowIn/stNumIn`。
- 落魄山小程序端 `.st-*` 是**裸类**（无前缀），故选择器统一加 `.sect-settle` 前缀限定，避免误伤。

### ⚠️ 关键坑：小程序端 setData 会重放动画（整页闪烁）
- `pages/*/*.js` 的 hook 是 `this.setData({ v: snap })`，**整体下发 v**。而 `view()` 里 `settle` 每次都新建对象+新数组 → WXML 节点被重建 → CSS 入场动效反复重放。结算后 `scFlushFx` 逐个飘字还会再触发多次 setData，闪烁更明显。
- **修法（引用缓存守卫）**：把结算视图缓存在 `s.lastSettle._v` 上，`view()` 命中则复用同一引用 → diff 判定未变 → 不下发 → 动画只播一次。
  - 山水祠：`weapp/utils/shenci.js` view() 的 settle 分支 `if(!st._v){ st._v = {...} } out.settle = st._v;`
  - 落魄山：新增 `sectSettleView(s)`，view() 改 `settle: sectSettleView(s)`
  - 换旬天然安全：`enterNext` 会 `s.lastSettle = null`，下次 settle 新建对象 → 新 `_v`，不会串旬复用旧账本。
- **PC 端不需要此守卫**：`innerHTML` 只在 settle 时写一次，飘字走 DOM 追加，不重绘。
